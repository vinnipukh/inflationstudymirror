# Plan 260816-fx4: Speed Up Streamlit + Falcon Dashboard

## Symptom

Dashboard is abnormally slow (multi-second waits on every interaction).

## Diagnosis (measured)

- `load_filtered_history` (default filters: 3 retailers x 45 newest files)
  takes **~4.4s per request** and loads ~355k rows from 135 CSVs.
- There is **no server-side caching** for loaded history: every API request
  re-reads and re-parses the same CSVs from disk.
- One Streamlit rerun renders all four tabs, firing ~5 data requests with the
  same / overlapping filters (history options, retailer averages, movers,
  coverage, product history) -> **~18-22s of API CPU per interaction**.
- `parse_common_filters` costs ~0.37s per request (inventory range + file-count
  computations) and is recomputed for every request.
- CSV engine `sep=None, engine="python"` is only marginally slower than a
  sniffed `engine="c"` (~0.70s vs ~0.62s per 45 files) -> engine swap is NOT
  the bottleneck; skip it.
- Frontend `api_client` opens a fresh HTTP connection per request (no
  keep-alive session).

## Tasks

1. **Server-side combined-history cache** (`filters.py`):
   - Cache `load_filtered_history` results keyed by a hashable filter
     signature: `(retailers tuple, start iso, end iso, max_files,
     all_history)`.
   - Stdlib-only TTL+LRU (functools/collections/time), TTL 300s, maxsize 8,
     skip entries > 350k rows (protects memory; combined frames ~62MB/355k
     rows), return `.copy()` so callers cannot mutate the cached frame.
   - `clear_history_cache()`; also make `clear_inventory_cache()` clear all
     data caches (the "files changed" signal).
2. **Per-file product-frame cache** (`csv_price_repository.py`):
   - Cache the built product frame per CSV keyed by `(path, mtime_ns, size)`,
     TTL 600s, maxsize 512, skip frames > 200k rows. Overlapping filter sets
     (options vs product detail vs date-range tweaks) reuse parsed files.
   - `clear_price_cache()`.
3. **Dedupe common-filter parsing** (`filters.py`):
   - Cache `ParsedFilters` by raw request signature (retailer list, dates,
     max_files, all_history) with the same TTL cache, removing the repeated
     ~0.37s/request inventory-range cost. Deterministic because inventory is
     itself cached.
4. **Frontend keep-alive** (`api_client.py`):
   - Module-level `requests.Session()` reused by `fetch_endpoint` (HTTP
     keep-alive instead of new connection per request).

## Out of scope (deferred)

- Trimming the ~355k-row options payload from `/api/history` (would change the
  API contract; separate plan).
- Streamlit fragment/lazy-tab refactor (UX-risky rerun semantics change).

## Risks

- Memory: mitigated by row caps + maxsize + TTL; measurable via size_mb of
  frames.
- Staleness: new scraped CSVs are picked up after cache expiry (<=5 min) or
  when `clear_inventory_cache()` is called (data pipeline hook).
- Thread safety: cache guarded by a lock (waitress = multi-threaded worker).
