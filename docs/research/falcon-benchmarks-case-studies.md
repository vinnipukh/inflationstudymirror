# Falcon Framework: Benchmarks & Real-World Case Studies — Research Notes

**Scope:** What benchmarks and production retrospectives actually say about Falcon (Python, falconry/falcon 4.3.1) performance, and what scaling pitfalls real teams hit. Grounded in the `inflationstudymirror` repo (Falcon 4.3.1 WSGI API, orjson handlers, in-process TTL caches, read-only WAL SQLite with mmap, Granian/Gunicorn-gthread/Waitress launchers, Python 3.14.7).

*Research date: 2026-09-03. All TechEmpower figures below were extracted from the official round results JSONs (via Wayback snapshots of techempower.com) and cross-checked against round blog posts.*

---

## Executive summary

- **Falcon's framework overhead is among the lowest of any Python web framework**, but the gap only shows once the *server* is competent. Same Falcon 4.x app: ~15k req/s under Gunicorn's default `sync` worker (the-benchmarker continuous suite), ~120k req/s under Granian WSGI, ~715–903k req/s under Gunicorn+Meinheld on TechEmpower Round 23's new hardware [^1][^6][^9]. Server/keep-alive choice swings results 8–60x; most "Falcon is slow" comparisons are measuring the server, not the framework [^6][^11].
- **Falcon wins on bare-metal WSGI overhead and CPU-bound/light endpoints; it loses on I/O-bound concurrency** — a WSGI thread pool caps throughput at ~pool size under blocking I/O, while ASGI (Falcon-async, FastAPI, Starlette, Robyn) scales with connection count: ~16.5k vs ~68k req/s for a 27ms simulated I/O workload [^6]. This repo's endpoints are CPU/DB-aggregation-bound, so Falcon-WSGI is the *right* tool; async would not help and would add complexity [^6][^12].
- **The repo's SQLite pattern (read-only `mode=ro` + WAL + busy_timeout=5000 + mmap) is documented-best-practice for read-mostly APIs, with two sharp edges**: (1) WAL + short-lived per-query connections can throw rare `SQLITE_BUSY` even with zero writers, because connection open/close cycles briefly lock `-shm`/`-wal` (SQLite docs §9; Hynek's 2026 repro) [^15][^16]; (2) after a writer's last connection closes, SQLite deletes `-shm`/`-wal`, so a read-only connection then needs *directory* write permission to recreate them [^14].
- **Benchmark number hygiene**: treat TFB R21↔R22 Falcon deltas (328k→272k req/s) as hardware/throttling noise (TFB's own issue #8397 documents CPU throttling after a machine move), not a Falcon regression [^8]; treat single-source microbenchmarks ([single-source]) as directional only — e.g. content-farm articles claiming "2.5M req/s" for Falcon are fabricated [^21].
- **Stock Waitress is a throughput liability for this workload** (1,067–1,448 req/s in TFB max-concurrency tests [^1]) and it is currently the *only* server declared in the repo's `pyproject.toml`/`uv.lock` (Granian/Gunicorn are referenced by the launcher but not declared as dependencies) [^28].

  * Net: Falcon ≈ 1.6x FastAPI and ≈ 11x Django on the same server; slightly behind Rust/blacksheep-class frameworks.
- **Wolfrahm/rahm_http_benchmarks_py (Falcon 4.3.1 / FastAPI 0.138 / Starlette 1.3.1 / Robyn, Python 3.13, M1 Max, 9 processes, per-workload tuning, wrk/oha)** [^6] [single-source]:
  * Ping (raw throughput, c500): Falcon+Granian (threaded) 120.4k; Falcon+Uvicorn (async) 142.3k; Starlette async 146.2k; FastAPI async 121.9k; FastAPI threaded 54.5k.
  * CPU (100 UUIDs/req, c100): Falcon threaded 11.2k vs Falcon async 14.0k; FastAPI async 14.1k — all ≈ core-bound; GIL means threads don't help CPU work within a process.

  * The same repo documents that Falcon served by **Gunicorn's default sync worker** (connection closed per response, no keep-alive) was ~12x slower than the same app on Granian — "Earlier rounds made Falcon look slow, but they were really measuring Gunicorn" [^6][^11].
- **Deploy Mastery 2023 (single vCPU, docker, wrk 20s)** [^11] [single-source]:
  * Hello world: falcon-bjoern 62,733; falcon-uwsgi 13,711; falcon-uvicorn(+uvloop) 8,066; falcon-gunicorn 6,551; flask-gunicorn 4,279; raw fastwsgi 214,112.
  * JSON (5.5KB): falcon-bjoern 15,756; falcon-uwsgi 6,528; falcon-gunicorn 4,799; flask-gunicorn 3,074.
  * CPU-bound (~90ms hog): *every* WSGI stack ≈ 11 req/s on one core (GIL serializes); PyPy + bjoern 395 req/s.
  * Takeaway: on 1 core and trivial payloads the *server* (bjoern vs gunicorn) is a 10x lever; Falcon's own overhead is second-order.
- **the-benchmarker/web-frameworks continuous suite (2026-08-29, M1 8-core, Python 3.14)** [^9] [single-source]: Falcon 4.2 (engines: gunicorn/uwsgi/waitress [^10]) — **14,942 / 14,769 / 14,615 rps at c64/256/512** with average latency exploding 3.3→33.6ms, while fastapi 42.3k/49.9k/52.0k, starlette 76.3k/81.3k/81.8k, flask 7.6k/8.0k/8.3k, django 1.5k/4.5k/4.4k, blacksheep 81.8k/85.7k/85.6k. #### 1.3 Methodology critique (cross-cutting)

- **Server > framework**: the same Falcon app swings 15k→120k→715k+ req/s purely on WSGI server (gunicorn-sync / granian / gunicorn+meinheld) [^6][^9][^13].
- **Sync vs async is workload-dependent**: for this repo (pandas aggregation over 350k rows, cached bytes), work is CPU-bound → processes are the lever; threads don't multiply CPU under the GIL [^6][^11]. Free-threaded CPython 3.14 changes that (see §2.4) [^17].
- **Hardware/network drift**: TFB rounds are not comparable across hardware generations [^2][^5]; TFB's Falcon json numbers on the old i7-era gigabit network were partially network-saturated [^7].
- **Concurrency levels**: TFB reports max-request-rate runs (c≈4096 equivalent); latency at that point can be multi-ms even for fast frameworks [^1].
- **Content farms fabricate**: johal.in's "2.5M req/s / 300% faster" Falcon piece (Nov 2025) cites no reproducible source and is AI-generated [^21]. Exclude from evidence.

### 2. Known ceiling: where Falcon wins and loses

- **Framework overhead**: Falcon is a minimal WSGI/ASGI framework; the README's positioning ("same hardware, more requests than Django/Flask", Cython-compiled wheels, PyPy-friendly) matches controlled microbenchmarks (klen: 1.6x FastAPI, 11x Django on the same server; Deploy Mastery: ~2x flask on same gunicorn) [^12][^11][^18].
- **GIL**: CPU-bound work inside one WSGI process is serialized; multiple *processes* are the standard scaling lever (TFB uses workers=cpu×1.5 [^3]); threads help only for I/O overlap. Deploy Mastery's CPU-hog test shows all single-process WSGI stacks ≈ 11 req/s on 1 core [^11].
- **Framework-overhead share in real endpoints**: for DB-backed endpoints (TFB db/query/update: 27–110k req/s) and for this repo's aggregation endpoints (seconds of pandas work, cached), framework overhead is a rounding error. The 2015 HN thread's Amdahl's-law argument is still the correct mental model — the web tier is rarely the bottleneck when handlers do real work [^19].
- **Where Falcon loses**: sustained high concurrent blocking I/O (per-request remote calls, streaming) vs ASGI event loops (~4-5x, rahm I/O test) [^6]; and developer-ecosystem convenience features (OpenAPI, validation, auth middleware ecosystem), not raw speed.
- **Serialization**: orjson dumps ≈ 10–14x stdlib json (vendor benchmarks; 92MiB numpy array: 105ms vs 1,481ms, RSS 105 vs 295MiB) [^24]; TFB cross-check: orjson endpoint variant +26% over stdlib in R23 [^1]. Falcon's JSONHandler accepts custom `dumps`/`loads` and the docs explicitly recommend orjson/msgspec/rapidjson/mujson (PyPy caveat: keep stdlib) [^25]. The repo's `resp.data=raw_bytes` + `content_type=MEDIA_JSON` pattern bypasses the media handler entirely on the hot path — correct and idiomatic.
- **Free-threaded CPython 3.14 (directly relevant — repo runs 3.14.7)**: Falcon 4.2+ ships wheels for the free-threaded 3.14 build; the maintainers load-tested WSGI on Gunicorn 23 + free-threaded 3.14.0 and report no GIL-leftover issues, with throughput scaling "almost linearly" with threads up to cores [^17]. Caveat: pandas/numpy's free-threading support is still version-sensitive (pandas requires NumPy ≥2.3.3 on Python ≥3.14 as of early 2026; free-threaded wheels exist for pandas 2.3.3/3.14t) [^27]; orjson itself only "may" support PEP 703 once stable [^24]. Not yet a default-branch recommendation; revisit when the whole stack ships free-threaded wheels.

### 4. Scaling pitfalls real teams hit

1. **Gunicorn default `sync` worker** (no keep-alive; connection closed per response; one request at a time per worker): the #1 way to make Falcon look 10–60x slow; fixed by gthread/gevent/Meinheld/Granian [^6][^9][^11][^32].
2. **Stock Waitress under concurrency**: single process, Python `asyncore` loop, default 4 threads → 3 orders of magnitude below Meinheld/Granian in TFB; TFB latency at peak ≈ 88–143ms [^1][^4][^20]. Waitress is fine for small admin/prototype loads; not for this repo's main path.
3. **Worker × cache memory blowup**: per-process caches multiply with workers. This repo caches per worker: DataFrame history cache (300 MiB budget), response cache (≤512 entries of `bytes + dict` ≈ 2x payload memory each), parse cache. 4 workers × (300 MiB + response bytes + pandas working set) can exceed 2–3 GB RSS before any request traffic; the `resp.media = envelope_dict` + `resp.data = raw_bytes` pair doubles the cached representation by design [^28]. Mitigations: lower per-worker budgets (worker-count-aware), store only bytes, warm cache once per worker (fork-Copy-On-Write: build large immutable payloads *before* forking workers if the launcher supports preload), or move the hot cache to shared memory/Redis.
4. **Naive per-request DB connections**: opening a new SQLite connection per query call (this repo: `get_db_connection()` per helper call, multiple per request) is cheap for mmap'd reads but multiplies the WAL `-shm` open/close lock windows (§5) [^16]; under high concurrency it also burns syscalls. A small per-worker connection pool (or one persistent read-only connection per worker/thread with `check_same_thread=False`) removes the churn [^16][^28].
5. **Blocking calls in async mode**: if the repo ever moved to Falcon-ASGI, pandas/SQLite (blocking) calls would stall the event loop unless wrapped in `anyio.to_thread`/a worker pool — the standard pitfall [^6].
6. **Huge JSON payloads (this repo's 350k-row history)**: pitfalls observed in the wild: double serialization (Python dict → json → bytes), per-cell Python conversion loops (the repo already avoids the re-walk with `JsonSafeList`), unbounded in-cache growth, and client-side parsing cost; orjson can serialize *column-oriented* numpy arrays natively ~10x faster than `tolist()`-style conversion and with lower peak RSS (105ms/92MiB vs 1,481ms stdlib) [^24] — but the API contract here is a list of row-dicts, so the win is only available if the payload format changes (e.g., column-major envelope or NDJSON stream). Pagination/thresholds already exist (`warnings` for >5k rows) [^28].
7. **Caching misuse**: TTL caches keyed by endpoint+query_string are correct here; pitfalls are stale-query cardinality (unbounded distinct query strings → cache thrash/eviction), and caching *before* auth/permission checks (not applicable here — public data).
8. **Middleware overhead**: CORSMiddleware runs per request; TFB-class numbers assume minimal middleware. CORS + JSON media handling kept minimal is the right shape for this app [^28][^25].

### 5. SQLite-specific: read-only + WAL + mmap (this repo) and when to move to PostgreSQL

- **WAL read-only rules (sqlite.org, authoritative)** [^14]: WAL-mode DBs cannot be opened read-only *unless* (a) `-shm` and `-wal` and already exist and are readable, or (b) the directory is writable so they can be created, or (c) `immutable=1` is used. **The repo's `mode=ro` URI works today because the dir is writable and the -shm/-wal exist [^28]**; but if the API runs from a read-only container/filesystem or an operator deletes `-wal`/`-shm` after a checkpoint, read-only opens break. Since the ingest pipeline writes and closes, the last writer's close deletes `-shm`/`-wal` (normal WAL cleanup [^14]) — briefly pushing all readers into the "must create files" path: keep directory write permission or ship with prepared `-shm`/`-wal`, or use `immutable` only if the DB file is truly static.
- **WAL busy behavior (authoritative + real-world repro)** [^14][^15][^16]: even with zero application writes, WAL can return `SQLITE_BUSY` to a query when (1) another connection holds exclusive locking, (2) the *last* connection closes and cleans up `-shm`/`-wal` under an exclusive lock, or (3) a crashed last connection triggers recovery. Hynek's TIL (2026) reproduces rare `database is locked` for a read-only-WAL, open-query-close-per-request pattern — exactly this repo's access pattern — mitigated by `busy_timeout` (the repo sets 5000ms, matching community guidance [^33]); the failure mode only disappears if connections are persistent.
- **Concurrency model**: WAL = many concurrent readers + one writer; readers do not block writers [^14]. For a read-heavy API over a static snapshot this is the ideal fit — the official "Appropriate Uses" doc: SQLite "competes with fopen()", excels at local, single-host, read-mostly data; client/server DBs are for shared/writable/centralized enterprise data [^34]. OneUpTime's 2026 production checklist corroborates: read-heavy, <~1000 writes/sec, few concurrent writers → SQLite with WAL is "excellent"; many concurrent writers or multi-host → PostgreSQL [^33].
- **mmap**: `PRAGMA mmap_size` default is off (0); sqlite.org recommends "usually 256MB or larger"; mmap removes kernel-buffer copies but (a) I/O errors on mapped pages become signals (SIGBUS on truncated files, SIGSEGV on I/O error) instead of SQLite errors, and (b) Windows can't truncate mapped files [^35]. **Note an in-repo inconsistency: the adapter sets `mmap_size = 1 GiB` and `cache_size = -128000`, while the launcher factory sets 256 MiB / -64000 [^28]** — reconcile to one value. DB is 2.8 GB / 4.1M rows today [^28]; 1 GiB mmap covers only part of the file, which is fine for hot-page locality but means cold history scans still go through `read()` syscalls.
- **When to move to PostgreSQL — and what it costs**: move when any of: multiple concurrent writers, cross-host/multi-process writers, need for network access to the DB, or query patterns that outgrow SQLite's single-file/single-writer model [^34][^33]. Cost for this repo: PostgreSQL adds a server process + auth + connection pooling (SQLite's `sqlite3.connect` one-liner disappears), schema/type friction (TEXT dates → DATE, REAL → NUMERIC), pg-specific backup/HA ops; and TFB shows Postgres-bound endpoints *lower* framework throughput ~7-15x vs cached/plaintext (JSON 715k → db 107k) — the migrations only pays off if the write/concurrency model genuinely needs it. For the current shape (ETL writes a snapshot, API read-only), keeping SQLite and making the reader side robust is the lower-cost, higher-performance option [^34][^33][^36].

## Recommended actions for the repo (prioritized)

1. **P0 — Ship Granian (or Gunicorn gthread) as the declared default; stop defaulting to Waitress.** `pyproject.toml`/`uv.lock` currently declare only `waitress`; the launcher's `--engine granian`/`gunicorn` paths require packages that aren't installed. Add `granian` (fastest WSGI per two independent sources [^6][^13]) and `gunicorn` to deps; keep Waitress only as a small-dev fallback. Expected effect at this workload: multi-worker Granian/`gthread` gives keep-alive + a real thread pool (sync-worker "connection per request" regression is the single biggest Falcon performance trap [^6][^11][^32]).
2. **P1 — Reconcile SQLite tuning constants (one source of truth).** Adapter: `mmap_size=1GiB`, `cache_size=-128000`; launcher factory: `256MiB`, `-64000`. Pick per-worker targets (e.g., `mmap_size = min(file_size, 1GiB)`, `cache_size=-128000`) and derive both from one module constant. With the DB at 2.8GB, consider raising mmap up to ~file size only if hot-set scans show syscall reads.
3. **P1 — Convert per-query SQLite connections to a small per-worker pool (or one persistent read-only connection per thread).** Keep `mode=ro` + `busy_timeout=5000` + `query_only=ON` + WAL; this eliminates the open/close `-shm` lock windows that cause rare `SQLITE_BUSY` for short-lived read-only WAL connections [^15][^16], and guarantees `-shm`/`-wal` stay alive between requests [^14].
4. **P2 — Right-size the per-worker caches for worker count; store bytes only.** The response cache keeps both `raw_bytes` and the full dict (≈2x memory per entry) and the DataFrame cache is 300MiB/worker; with N workers this multiplies. Store bytes only (`resp.data`), or make budgets `budget/workers`, or (if launcher supports preload/fork) build and warm caches before forking workers to exploit COW. Audit RSS under max-TTL traffic: 8 workers × (300MiB df-cache + response bytes + working set) is the realistic blowup scenario [^28].
5. **P2 — Keep the Falcon-WSGI choice; do not migrate to ASGI for this workload.** All heavy paths are CPU/DB-bound and already byte-cached; async would add an event-loop/threadpool split with no throughput gain (sync-vs-async gap only appears for concurrent blocking I/O) [^6]. If the team ever wants more per-CPU parallelism, first test Falcon on **free-threaded CPython 3.14** (Falcon 4.2+ ships 3.14t wheels and the maintainers' Gunicorn load test scaled ~linearly with threads [^17]) — but only after confirming pandas/numpy free-threading support for the pinned versions [^27][^24].
6. **P3 — Verify payload-size behavior against WSGI servers.** Confirm no proxy in front truncates/timeouts 10–50MB history responses (keep-alive + `Content-Length` from `resp.data` are fine); Waitress has a default `max_request_body_size=1GB` (irrelevant for GETs, but document it); consider gzip/brotli for large cached payloads at the edge if bandwidth matters [^20]. If payload sizes keep growing, evaluate NDJSON or column-major envelopes to exploit orjson's native numpy path (~10x serialization speedup with lower peak RSS) — requires an API-contract change with the Svelte client [^24].
7. **P3 — Add a smoke benchmark script** (wrk/oha) modeled on rahm's methodology: same machine, keep-alive, 3 endpoints (health/ping, cached history, uncached small query) across granian-{1,4} workers, gunicorn-gthread-{4,16}, waitress; record req/s+latency. This resolves the 15k-vs-715k confusion for *this* stack in minutes and catches server-config regressions [^6][^9][^13].
8. **P3 — Update docs**: record in `docs/TECH-STACK-SEARCH.md` the server-choice sensitivity (gunicorn-sync vs granian vs meinheld), the WAL-read-only constraints, and the free-threading status — per AGENTS.md's living-docs convention.

## Gaps & uncertainty

- **TFB absolute numbers are hardware+network-specific**: R22 vs R23 differ 2-3x for the same stack due to new servers/40GbE [^1][^2]; cross-round quotes must cite the round. R21→R22 Falcon deltas partly reflect CPU throttling after a machine move (TFB issue #8397) [^8] — [single-source] for the throttling explanation.
- **All non-TFB microbenchmarks are single-source**: rahm (M1 Max, 9 procs, c2000), Deploy Mastery (single vCPU, docker), the-benchmarker (M1, gunicorn-class server), Granian vendor bench — each is internally consistent and they agree directionally (server choice ≫ framework overhead; async wins only for concurrent blocking I/O), but exact req/s should not be compared across machines [^6][^9][^11][^13].
- **the-benchmarker Falcon result likely measures a suboptimal server config** (gunicorn default engine; flat rps + 3.3→33.6ms latency growth at c64→c512) — I could not fully verify which engine produced the posted numbers; treat its Falcon-vs-FastAPI comparison as invalid for framework ranking until confirmed [^9][^10].
- **Waitress TFB numbers use stock settings** (4 threads); Waitress with more threads would do better than 1.1-1.4k req/s but remains a Python-loop server — no controlled high-thread Waitress benchmark was found.
- **Free-threaded CPython 3.14 for this repo is unverified end-to-end**: Falcon's own wheel+load-test statement is authoritative for Falcon [^17], but pandas/numpy free-threading maturity is version-sensitive [^27] and orjson's PEP 703 support is not yet shipped ("may support when stable") [^24]. Must re-check pinned versions before adopting 3.14t.
- **Case-study list is self-reported** for everything except LinkedIn/Iris and Mailman (verified in code) [^18][^26][^29][^30]; Open edX, Mailchimp, Rejected.us show no evidence of Falcon use [^31].
- **SQLite behavior claims** rely on sqlite.org docs (authoritative) [^14][^35] plus one 2026 field repro (Hynek) [^15]; the exact frequency of `SQLITE_BUSY` for this specific repo's workload (2.8GB DB, 4.1M rows, 982 ingested files, per-query connections, busy_timeout=5000) was not measured — the recommendation to pool connections is prophylactic.
- **Version-sensitive advice**: falcon unpinned in pyproject (currently 4.3.1 per task); orjson>=3.12; Waitress>=3.0.2; Granian/Gunicorn absent from deps — all recommendations assume the launcher's intended engines and should be re-validated when pins change.
- **No large-JSON payload public benchmark** specifically for Falcon was found; payload guidance is inferred from orjson vendor benchmarks [^24], TFB json-test deltas [^1], and the repo's own code [^28].
