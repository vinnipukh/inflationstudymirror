# Falcon Deployment & Server Tuning — Research Notes

Scope: how to deploy/tune a Falcon **WSGI** backend (Granian / Gunicorn / Waitress / uWSGI / Uvicorn) for maximum throughput, grounded in this repo: Falcon 4.3.1, Python 3.14.7 (GIL build), WSGI `falcon.App` + CORSMiddleware + orjson media handlers, pre-serialized byte responses served from an in-process TTL cache, read-only SQLite (WAL, mmap) data layer, launcher at `scripts/run_falcon_server.py` supporting Granian/Gunicorn/Waitress/Uvicorn.

Date of research: 2026 session. Versions verified on PyPI and in the repo venv: granian 2.8.2, gunicorn 26.2.0, waitress 3.0.2, uvicorn 0.52.4, hypercorn 0.18.0, uwsgi 2.0.31, falcon 4.3.1 [^25].

## Executive summary

- **Granian (Rust/Hyper, WSGI mode) is the best throughput choice for this app and the launcher already defaults to it.** Official benchmarks: ~125k rps single-worker WSGI vs ~9.2k (gunicorn gthread), ~12.2k (uWSGI); e.g. 6–13× on raw serving [^1]. Local loopback measurement on this repo's real Falcon app (health + cached inventory, Python client): granian 2w×8t ≈ 5.1k rps vs gunicorn gthread 2w×8t ≈ 3.5k, waitress 16t ≈ 3.5k, gunicorn sync 4w ≈ 2.1k — i.e. **granian ≈ +45% over gthread/waitress and +140% over sync** even with a client-side ceiling [^27]. Because this app mostly re-serves cached `bytes` (tiny per-request Python work), server/socket efficiency dominates, which is exactly Granian's advantage.
- **Workers scale; threads mostly don't.** Endpoints are CPU-bound (pandas aggregations) under the GIL, so the lever is process count: Gunicorn guidance is 2–4 × cores [^5]; Granian's author says keep Python-side threads ≤ ~2N cores [^4]. Repo defaults (workers=min(cpu,8)=8, threads=16/worker) are over-threaded; recommend workers ≈ cores (8 on 16-core), threads 4–8/worker, and reserve more threads only for I/O-bound paths.
- **Three of the four launcher engines are misconfigured today:** (a) waitress engine passes a *factory name*, Waitress calls it as a WSGI app → 500 [verified on this repo] [^15][^27]; (b) uvicorn engine passes only `--factory` without `--interface wsgi` → WSGI app invoked as ASGI → 500 [verified]; fix = `--interface wsgi` (deprecated per Uvicorn docs; a2wsgi recommended) or switch to `falcon.asgi.App` [^16][^27]; (c) gunicorn gthread engine is correct as written.
- **Connections/kernel**: put nginx (or Caddy) in front with TLS, upstream keep-alive (`keepalive 32; proxy_http_version 1.1; proxy_set_header Connection "";`) [^23], `--keep-alive` 2–5s behind proxy [^5], raise `somaxconn/tcp_max_syn_backlog` to ≥ backlog (2048), bump `ulimit -n`, and use `max_requests` + jitter (gunicorn) or `--workers-lifetime/--workers-max-rss` (granian) for leak control [^7][^9][^3].
- **HTTP/2 is a non-goal for this workload**: JSON API + separate static SvelteKit frontend; browsers multiplex static assets, not API calls. Only matters if you serve the SPA from the same origin. Gunicorn 25+ has beta h2 (gthread only) [^9]; Granian has h2 (benchmarked on ASGI; WSGI-h2 unverified) [^1][^2].

## Findings

### 1. Server comparison (Gunicorn, uWSGI, Waitress, Granian, Uvicorn/Hypercorn)

**Granian 2.8.2** — Rust HTTP server on Hyper+Tokio; single package serving ASGI/3, RSGI and **WSGI**; HTTP/1 + HTTP/2, TLS/mTLS, websockets (not on WSGI), static file serving, and per-worker `--blocking-threads` for WSGI [^2][^3]. Official benchmark (AMD Ryzen 7 5700X, 16 cores, Py 3.13, 1 worker, 10KB GET/POST): WSGI mode with 1 blocking thread ~125.8k rps (avg lat 0.51 ms) vs gunicorn gthread 9.2k (6.96 ms), gevent 11.8k, uwsgi 12.2k; echo: 108k vs 6.7k/8.3k/9.3k [^1]. Main author: "Granian can only affect the network part… still subject to GIL and blocking code"; `--threads` are Rust threads, Python-side concurrency = `--blocking-threads`; use ≤2N threads [^4]. Trade-offs: not pure-Python, no gevent/trio, ASGI extensions incomplete (issue #93), fast-moving project (2.8.x in 2026; 2.x line changed CLI names e.g. `--threading-mode` → `--runtime-mode` autodetect) [^2][^4].

**Gunicorn 26.2** — pre-fork arbiter model; worker classes: sync (default, one request at a time, **no keep-alive**, needs buffering proxy), gthread (thread pool; supports keep-alive; good for mixed workloads), gevent (greenlets; needs lib patches; thousands of conns), ASGI workers, tornado [^6][^7]. Raw single-worker throughput is far below Granian/uWSGI (official granian benchmark above; also Tier2 blog comparisons) [^1][^21]. **25.0 added beta HTTP/2** (requires SSL/TLS h2 or h2c; recommended with gthread worker) [^9][^10]. 26.0.0 (2026-05) contained breaking changes; 26.2.0 shipped HTTP/2 bug fixes [^10]. Workhorse, boring, best-documented; the safest default if you distrust a Rust server.

**uWSGI 2.0.31** — the Falcon docs' recommended companion ("NGINX + uWSGI = one-two punch") [^11]; in granian's bench it beat gunicorn gthread (12.2k vs 9.2k on GET; much slower on 100ms I/O simulation: 54 rps vs 5.0k) [^1]. Notoriously complex config; C extension build friction on new Pythons (2.0.x releases attempt it; on 3.14 check wheel availability) [^25].

**Waitress 3.0.2** — pure-Python, battle-tested, one process/thread pool; defaults: threads=4, backlog=1024, **connection_limit=100** (low!), max_request_header_size=256KB, channel_request_lookahead=0 [^14][^15]. Its own issue tracker shows nginx 504s when `connection_limit` is too low and 2.1.0 perf regressions [^19][^20]. Slower than gunicorn gthread in this repo's local test (3.5k ≈ gthread) [^27]; fine for small deployments, not the throughput answer. Windows-safe pure-Python is its niche.

**Uvicorn 0.52 (ASGI)** — built on uvloop+httptools (or h11); production guidance: `gunicorn -k uvicorn.workers.UvicornWorker` behind nginx/CDN [^17]. Settings: `--timeout-keep-alive` default 5, `--backlog` default 2048, `--limit-concurrency` (application-level 503 cap), `--limit-max-requests`+jitter (leak control) [^16]. **Native `--interface wsgi` exists but is deprecated → use a2wsgi** [^16]. Benchmarks: httptools ~51k → 62k rps (echo) vs granian 125k [^1]. Not relevant to this repo unless you port the app to `falcon.asgi.App`.

**Hypercorn 0.18** — flexible (h1/h2/h3, trio/asyncio) but slowest in benchmarks (9.3k GET; h2 7.3k) [^1][^25].

**Which pairs best with Falcon WSGI:** Granian WSGI (`--interface wsgi --blocking-threads N`) — purpose-built for exactly this sync-Falcon stack; gunicorn gthread as the conservative fallback. Falcon's own ASGI flavor (`falcon.asgi.App`, 3.0+) pairs with uvicorn/hypercorn [^13][^30], but the repo's app is deliberately WSGI + sync pandas code; converting buys multiplexing but loses Granian's byte-serving advantage unless you keep per-worker caches (they survive as-is).

### 2. Worker/thread sizing, GIL, preload, max_requests

- Gunicorn: `workers` = "positive integer generally in the 2–4 × NUM_CORES range" (official docs; the widely-quoted `2*CPU+1` is the older formula from the same lineage) [^5]. `threads` (gthread) similarly "2–4 × NUM_CORES" [^5]. Setting `--threads N` with sync auto-upgrades to gthread [^5].
- GIL: CPython 3.14.7 in this repo is the standard GIL build (verified `sys._is_gil_enabled()=True`); pandas/numpy release the GIL for parts of vectorized ops, but Python-level housekeeping and CJK of the request path hold it — so multiple **processes** are the reliable scaling unit for cache-miss computation; threads mainly help when requests block on I/O (sqlite reads, socket writes) [^4][^26].
- **Falcon is GIL-free-threading compatible for 3.14**: Falcon ships binary wheels for free-threaded CPython 3.14 and reports near-linear thread scaling under Gunicorn 23 on FT 3.14.0 — an option to revisit if this box ever runs `3.14t`, but untested at this repo [^12].
- Granian WSGI blocking threads: `--blocking-threads` per worker; **if omitted, the default is `max(1, backpressure//2)` where backpressure = backlog/workers — with backlog 1024–2048 that silently spawns 512–1024 Python threads/worker** (verified in granian source) [^3]. Always pass it explicitly (launcher does).
- `preload_app` (gunicorn `--preload`): loads the app before fork → RAM savings via COW and faster boot; but it also means the unified cache is populated once pre-fork (children copy-on-write; each child keeps its own) and reload requires full restart; fine for this app, modest benefit [^5]. Granian has no preload flag; each worker builds its own caches naturally.
- `max_requests` + `max_requests_jitter` (gunicorn): worker recycle after N requests to bound memory leaks; jitter staggers restarts [^5]. In-process caches here re-warm per worker after recycle (TTL 300s caches + up to 300MB history cache) [^27] — pick max_requests large enough (e.g. 10k–50k) that recycle cost is amortized. Granian equivalents: `--workers-lifetime` (min 60s), `--workers-max-rss` (MiB-based respawn), `--respawn-failed-workers` (default off), `--workers-kill-timeout` [^2][^3].
- This repo: CPU-bound pandas cache-miss paths benefit from workers ≈ cores (8 on this 16-core box); threads 4–8/worker is enough for sqlite page-cache reads and socket handling; 16 threads/worker × 8 workers = 128 Python threads per process set is wasteful and increases GIL contention on misses [^4][^27].

### 3. Connection-level tuning

- **keep-alive**: gunicorn `--keep-alive` default 2s; docs: 1–5s when direct to clients, higher behind LB/nginx (since proxy holds connections) [^5]; sync workers ignore it (no keep-alive) [^5][^7]. Granian: `--http1-keep-alive` default **enabled**, no configurable h1 keep-alive idle timeout in 2.8 CLI (only `--http1-header-read-timeout` 30s; h2 has ping-based keep-alive) [^2][^3]. Behind nginx, the proxy's `keepalive_timeout 65` governs client side and `upstream keepalive` governs server side.
- **timeout**: gunicorn `--timeout` 30s default kills silent workers; for gthread/gevent it only tests worker liveness, not per-request duration; for sync it bounds a request; set to 0 = infinite (not recommended) [^5]. `--graceful-timeout` 30s bounds graceful restart; longer = safer for long pandas aggregations [^5]. nginx side: `proxy_read_timeout`/`proxy_send_timeout` ≥ app timeout.
- **backlog**: gunicorn `--backlog` default 2048 (since 26.x; was 2048 earlier) [^5]; granian `--backlog` default 1024, min 128, plus `--backpressure` = concurrent in-flight requests per worker (default backlog/workers) [^2][^3]; uvicorn default 2048 [^16]; waitress 1024 [^14]. Kernel: `net.core.somaxconn` must be ≥ app backlog or the kernel caps the queue; gunicorn FAQ: `sudo sysctl -w net.core.somaxconn=2048` [^7]; for high concurrency: somaxconn + `tcp_max_syn_backlog` 65535, `netdev_max_backlog` 65535, `ip_local_port_range` widening, `tcp_tw_reuse=1`, `fs.file-max`, nofile 65535 via systemd/limits.conf [^9].
- **TIME_WAIT/ports**: aggressive short-lived connections pile TIME_WAIT sockets for 60s → port exhaustion under load; fixes: keep-alive on both sides (reduce connection churn), `tcp_tw_reuse` (Linux-only shortcut; beware NAT), widen ephemeral range [^9][^22]. `tcp_fin_timeout` shortening is the classic TIME_WAIT lever but modern guidance prefers above [^9][single-source for fin_timeout specifics: not verified in primary docs].
- **file descriptors**: raise per-process limit; sockets count as FDs; manage via systemd `LimitNOFILE` [^7]. Gunicorn heartbeat tmp: point `--worker-tmp-dir` at tmpfs to avoid fs stalls [^7].
- **HTTP/2**: gunicorn 25+ beta h2 with `--http-protocols h2,h1` + TLS (gthread recommended), tuning profiles (balanced: 4w×4t, backlog 2048; high-concurrency: worker_connections 10000, window 1MB) [^9]; granian `--http 2` (windows/max-concurrent-streams configurable) [^2][^3]; hypercorn h2 [^1]; uvicorn: no h2 flag in settings docs [^16]. For this repo: nginx-fronted h1 is fine; enable h2 at nginx if the proxy fronts browsers.
- **request limits**: gunicorn `--limit-request-line` 4094 default (raise/lower as needed for long query strings); limit-request-fields/fieldsize for header abuse [^5]. Waitress caps body 1GB, headers 256KB [^14]. Repo query strings are small (filters); defaults fine.

### 4. Deployment topology

- **Reverse proxy in front is strongly recommended** for gunicorn sync and recommended generally: nginx buffers slow clients (protects gunicorn from slowloris), terminates TLS, serves static assets, handles health/LB [^7][^8]. Falcon's official deployment guide: nginx + uWSGI for HA/scale; run app as separate user; unix socket or TCP upstream [^11]. Gunicorn's guide: same nginx pattern (`upstream app_server`, X-Forwarded-For/Proto/Host, `proxy_redirect off`; disable `proxy_buffering` only for streaming; `proxy_ignore_client_abort` for health-check churn) [^8].
- **Upstream keep-alive** (critical, often missed): `upstream backend { server 127.0.0.1:8000; keepalive 32; }` + `proxy_http_version 1.1; proxy_set_header Connection "";` — otherwise nginx opens a new TCP conn per request (TIME_WAIT storms, handshake latency) [^23]. With granian (h1 keep-alive on by default) this works and matters most.
- **TLS termination**: at nginx/Caddy (not in the app server); gunicorn http2 guide notes direct TLS+h2 possible with gunicorn 25+ but nginx is simpler [^9]. Caddy alternative: auto-https, but nginx has higher raw proxy throughput in Tier2 comparisons (e.g. ~310k vs ~285k rps static; 20% higher reverse-proxy throughput in another) [^24 — Tier2 single-source each; treat as indicative only]. Caddy 2.8 is fine for low-MB deployments.
- **Static assets / SvelteKit**: separate frontend (client-side SPA) — serve its build dir from nginx directly; the API behind `/api` proxy to the app server; do **not** route static files through Falcon/Granian's static-file feature for this repo [^8][^27].
- **Health checks**: use the existing `/api/health` endpoint; nginx passive checks via `fail_timeout`/`max_fails` or external LB probes; `proxy_ignore_client_abort on` if probes close connections abruptly [^8]. (Active `health_check` is nginx Plus; keep probes external/simple.)
- **Process management**: systemd unit (Restart=always, LimitNOFILE=65535, TimeoutStopSec ≥ graceful timeout; `kill -HUP` master for gunicorn config reload; `TTIN/TTOU` for dynamic worker counts) [^7][^8]. No container layer in this repo — systemd is the right manager.
- **Horizontal scaling**: stateless API + read-only SQLite per node (WAL read-only is multi-process safe; each process opens its own connection per request in this codebase — verified `search_products` opens+closes per call) [^27]; one nginx LB distributing to N app nodes; per-node in-memory caches duplicate (fine at this scale); put a CDN/cache on top for repeated responses ("CDN for caching support" per uvicorn docs) [^17][^18].
- **Caching layer placement**: this repo's in-process TTL cache is the most effective cache (byte responses) [^27]; add `Cache-Control`/ETag headers so CDNs can cache idempotent GETs (history/inventory/movers etc. vary by query filters; TTL matching the 300s app TTL is a safe CDN TTL) [^18 parity]. Don't add a second cache tier until traffic justifies it.

### 5. Granian specifics (repo already supports Granian)

- **WSGI mode**: `granian --interface wsgi app:app` is first-class; WSGI implies: keep-alive on by default, websockets disabled automatically [^2][^3]. The repo launcher already passes `--interface wsgi --factory inflation_dashboard.api.falcon_app:create_app` — correct combination (factory is supported via `--factory`) [^2][^27]. **Default interface is RSGI, not WSGI** — always pass `--interface wsgi` (launcher does) [^2].
- **Threads**: `--workers` = processes; `--blocking-threads` = Python threads per worker (WSGI); `--runtime-threads` = Rust tokio runtime threads (default 1); no `--threads` alias anymore (older 1.x had `--threads`; docs/discussions show the API moved to blocking-threads + runtime-threads + `--runtime-mode [auto|mt|st]`) [^2][^3][^4]. WSGI blocking-threads default = backpressure/2 (see §2) [^3].
- **Keep-alive/backlog defaults**: backlog 1024 (min 128); backpressure = backlog/workers; h1 keep-alive enabled; h1 header read timeout 30s; h2: adaptive window off, 1MiB windows, 200 max concurrent streams, ping keep-alive optional [^2][^3].
- **Leak/lifecycle controls**: `--workers-lifetime` (≥60s), `--workers-max-rss` MiB, `--respawn-failed-workers` (default disabled), `--workers-kill-timeout`, `--blocking-threads-idle-timeout` 30s [^2][^3].
- **Falcon compatibility notes**: no known Falcon-specific issues; the app is plain WSGI; CORS middleware is sync; orjson handlers sync — all execute inside blocking threads; responses already `bytes` → served with content-length, no chunking overhead [^27]. Granian WSGI runs the app off the Rust runtime via blocking-thread pool — so pandas work does not stall the acceptor [^1][^2][^4].
- **Version sensitivity**: granian is the fastest-moving server here (2.8.x in Aug 2026; CLI option renames across 1.x→2.x; `granian.dev` docs DNS unstable in this sandbox — rely on `granian --help`, the GitHub README, and DeepWiki mirror) [^2][^4][^25]. Re-verify `--help` before upgrading.

### Local benchmark (this repo, 2026 session) [^27]

Method: real Falcon app on Python 3.14.7 venv (granian 2.8.2 / gunicorn 26.2.0 / waitress 3.0.2 / uvicorn 0.52.3), loopback, 8s steady load, 24–128 concurrent keep-alive clients from a Python http.client harness (client itself ceilings around 5.2k rps; treat as *comparative*, not absolute).

| Server config | /api/health rps | /api/inventory (cached) rps |
|---|---|---|
| granian 2w × 8 blocking-threads | 5,110 | 5,045 |
| granian 4w × 8t | 5,225 | — |
| gunicorn gthread 4w × 4t | 4,397 | — |
| gunicorn gthread 2w × 8t | 3,503 | 2,950 |
| gunicorn sync 4w | 2,139 | — |
| waitress 16 threads | 3,536 | 3,486 |
| uvicorn wsgi 1w (--interface wsgi) | 2,631 | — |

Engine-correctness findings (verified on this repo): waitress engine (`waitress ... inflation_dashboard.api.falcon_app:create_app`) → `TypeError: create_app() takes 0 positional arguments but 2 were given` (500); `:create_app()` syntax rejected by waitress CLI ("invalid format"); fix = expose `app = create_app()` module. uvicorn engine (`uvicorn --factory ...:create_app`) → 500s; fix = `--interface wsgi` (works, verified) or a2wsgi wrapper. gunicorn gthread + granian engines run correctly [^27].

## Recommended actions for the repo (prioritized)

1. **Keep Granian as the default engine; fix its defaults.** Change `run_falcon_server.py` defaults: `--workers` = `min(os.cpu_count(), 8)` stays, but `--threads` default 16 → **8** (still safe) and document that `--blocking-threads` must always be explicit (granian may otherwise default to 512–1024 threads/worker with backlog 2048). Consider `--workers-lifetime` (e.g. 1h) or `--workers-max-rss` (e.g. 4–6 GiB given 300MB history caches + pandas frames) to match gunicorn's max_requests leak control. [^2][^3][^5]
2. **Fix the waitress engine** (or remove it): pass a real app object (`bench-style module` with `app = create_app()`), or drop waitress — it offers no throughput advantage here (3.5k vs granian 5.1k local). If kept, raise `--connection-limit` (default 100 is far too low for load testing) and `--backlog`. [^14][^15][^19][^27]
3. **Fix the uvicorn engine**: add `--interface wsgi` (verified working) or wrap with a2wsgi; better: delete the branch and note uvicorn is only relevant if the API migrates to `falcon.asgi.App`. Native uvicorn WSGI is deprecated. [^16][^17][^27]
4. **Add a gunicorn 26 sanity pass**: gunicorn 25+/26 changed worker-class behavior and added HTTP/2; verify `--keep-alive` (set 2–5), `--graceful-timeout` (≥ 60–120s so long pandas aggregations finish during restarts), and consider `--max-requests 10000 --max-requests-jitter 1000` if running gunicorn for long. [^5][^9][^10]
5. **Deploy nginx in front (or Caddy)**: TLS termination, serve the built SvelteKit SPA as static files, proxy `/api` to `127.0.0.1:8000` with `proxy_http_version 1.1; proxy_set_header Connection "";` and `upstream keepalive 32`. Set `proxy_read_timeout` ≥ gunicorn/granian timeouts; keep `proxy_buffering on` for the JSON API. Health-check `/api/health`. [^8][^17][^23]
6. **OS-level tuning (systemd/VM host, WSL note)**: `net.core.somaxconn` ≥ 2048 (kernel caps granian/gunicorn backlog otherwise), `net.ipv4.tcp_max_syn_backlog` 65535, widen `ip_local_port_range`, `tcp_tw_reuse=1`, `LimitNOFILE=65535` on the unit; mount `/tmp` check for gunicorn heartbeat tmpfs only if gunicorn is used. [^7][^9]
7. **Worker sizing on the 16-core target**: granian `--workers 8 --blocking-threads 4..8` (cache-miss path is CPU-bound pandas; keep-alive byte-serving is the cheap path); stress-test with >64 concurrent clients for headroom. Revisit only if 3.14t (free-threaded CPython) is adopted — Falcon already reports near-linear thread scaling there. [^4][^5][^12][^27]
8. **CDN/caching headers**: emit `Cache-Control: max-age=<300s>` + ETag on the idempotent GET endpoints to match the 300s in-process TTL cache, so a CDN can offload repeat requests; this is the cheapest throughput win after the engine. [^17][^18][^27]
9. **Document it**: extend `docs/TECH-STACK-SEARCH.md` / deployment docs with this server-selection rationale and the verified engine fixes (per AGENTS.md convention).

## Gaps & uncertainty

- **Local benchmark is client-capped and comparative, not absolute.** The Python http.client harness plateaus at ~5.2k rps; official Rust-based numbers for granian (125k) vs gthread (9k) are the reference for raw serving and were *not* reproduced here. Re-measure with a native loader (oha/wrk/h2load — none installed on this box) before tuning past these levels [^1][^27].
- **Granian HTTP/2 + WSGI is unverified** — official bench exercises h2 on ASGI only; WSGI-on-h2 depends on the hyper implementation [^1][single-source]. Assume h1 behind nginx unless tested.
- **Free-threaded Python (3.14t) claim is Falcon-maintainer self-reported** (gunicorn 23.0.0, 3.14.0) and untested in this repo; threading gains on this codebase are speculative [^12].
- **tcp_fin_timeout specifics** were not verified in Tier1 docs (covered by Tier2/3 lists only); prefer keep-alive + tcp_tw_reuse + widened ports as the primary levers [^9][single-source for fin_timeout].
- **Gunicorn "changed in 26.3"** marker in master settings docs suggests docs ahead of the 26.2.0 release; exact keep-alive default deltas across 26.x should be re-checked against the installed version's `--help` [^5][^10].
- **Caddy-vs-nginx performance numbers** come from Tier2 blogs with different methodologies (static vs reverse-proxy, machine-dependent); treat directionally only [^24].
- **uWSGI on Python 3.14** — wheel availability and build status on 3.14 were not verified here (2.0.31 is current); uWSGI's 100ms-I/O collapse in the official bench (54 rps) makes it unattractive for this workload anyway [^1][^25].
- **Granian docs site (granian.dev) DNS was unreachable in this sandbox**; CLI facts were verified against the installed 2.8.2 binary (`granian --help`) and source, which is treated as authoritative here [^2][^3].
