# Profiling, Database & Caching Optimization for the Falcon API — Research Notes

Research subagent output for topic: **PROFILING, DATABASE & CACHING OPTIMIZATION FOR FALCON**.
Repo grounded in `/mnt/e/Projects/inflationstudymirror` (Falcon 4.3.1 WSGI, orjson media handlers, pre-serialized byte cache, read-only SQLite, Granian/Gunicorn launcher).
All local measurements below were taken 2026-09-07 in the repo venv (`InflationItems/prices.db`, 2.68 GB, 4,094,300 rows in `price_observations`, SQLite 3.53.1, Python 3.14.7, pandas 3.0.5, orjson 3.12.0) unless labeled otherwise.

## Executive summary

- The API's hot path is **not** serialization or pandas groupby (54–83 ms on 425k rows) — it is the **first history load per filter signature** (measured 2.4 s for a 1-month window / 3.7 s for 3×45 files / 15 s for uncapped all-history) inside `load_price_history_from_db`, mitigated only by in-process TTL caches that duplicate per worker and expire every 300 s. [^local] [^local2]
- The cheapest whole-system wins are **HTTP-layer**: the 77 MB `/api/history` payload gzips to ~2 MB (2.4% ratio, 0.12 s CPU per 27 MB measured), and `Cache-Control` + `ETag`/304 make browsers and any CDN absorb repeated identical GETs — the code currently emits **no** cache headers and **no** compression. [^local3] [^28] [^27]
- SQLite tuning is mostly **already done** (WAL, busy_timeout 5000, mmap, `mode=ro`), and per-request `connect()` costs only ~20 ms; the real gaps are per-thread connection *reuse* (kills the 20 ms + pragma setup per request), a cold-start problem (OS page cache + in-process caches are empty at boot), and a 2.68 GB DB that exceeds the 256 MB/1 GB `mmap_size` configured in code. [^local2] [^9] [^13]
- The repo already contains SQL-side aggregation functions (`load_retailer_averages_from_db`, `load_movers_from_db`, `load_coverage_from_db`), but they are **unused by the API and measured slower than the pandas path** (3.0–18.1 s vs 2.4 s load + 54–83 ms groupby) because they scan 4.1M rows and cannot match the "45 newest files per retailer" semantics. Do not wire them in as-is; precompute per snapshot instead. [^local4]
- Serialization is already near-optimal for the current record format: `records_from_frame` (0.72 s / 310k rows) beats `to_dict('records')` (1.7 s) and `orjson.dumps` adds only 0.10 s on the 77 MB envelope; orjson is 2.8–8.7× stdlib json per published benchmarks. Remaining serialization wins are shape changes (column-major, msgspec structs) or skipping it entirely by serving cached bytes. [^local5] [^17] [^20]

## Findings

### 1. Profiling & observability

**Non-invasive sampling: py-spy.** `py-spy` is a Rust sampling profiler that attaches to a *running* CPython process — no restart, no code changes, <~20% overhead — with `py-spy top --pid <worker>`, `py-spy dump --pid` (per-thread stack traces), and `py-spy record --pid <pid> --format flamegraph -o prof.svg` for flame graphs. [^1] Not installed in this repo's venv or system (`py-spy` absent; only `falcon-bench`, `gunicorn`, `granian`, `waitress-serve` present). [^local] Recommended: `py-spy top` against a Granian/gunicorn worker while `wrk`/`ab`/`hey` (none installed either) drive `/api/history` and `/api/coverage`; latency outliers will show whether time is in `sqlite3` C calls, `pd.DataFrame` construction, `records_from_frame`, or `orjson.dumps`. [^local]

**cProfile + SnakeViz.** For one-request profiling, the cleanest path in this repo is Falcon's test client (`falcon.testing.TestClient(app)`), which runs the WSGI app in-process — wrap a single `on_get` for `/api/history?...` in `cProfile.Profile.runcall(...)` and dump to `.prof`, then view with SnakeViz (`pip install snakeviz`, `snakeviz file.prof`). [^2] [^3] cProfile is intrusive (slowdown several x), so use it for one-shot hot-endpoint analysis and py-spy for production truth. SnakeViz/cProfile can also be run against `scripts/test_sqlite_adapter.py` or `scripts/benchmark_db_queries.py` (they already exist and exercise the SQL layer end-to-end). [^local]

**Falcon middleware timing.** Falcon middleware is a class with `process_request(req,resp)` / `process_response(req,resp,resource)` hooks; a timing logger records `time.perf_counter()` in `process_request` (store in `req.context`) and logs the delta + route + query string + status in `process_response`. This is the documented Falcon recipe pattern (Request ID logging middleware). [^4] It costs microseconds per request and is the fastest way to get per-endpoint p50/p95 in this repo — the app currently has **only** `CORSMiddleware`, so a `TimingMiddleware` is a 30-line add to `inflation_dashboard/api/falcon_app.py`. Because responses are pre-serialized and cache-served, the middleware should also record a `cache_hit` boolean (the resources already know it before calling `_send_response`) so cache efficacy is observable per request. [^local]

**Structured access logs.** structlog is the standard structured-logging layer for WSGI frameworks; typical integrations add a middleware that captures method, path, status, duration, request_id into JSON lines, optionally forwarding to Datadog via an HTTP handler. [^38] Granian and Gunicorn (gthread) both emit their own access logs with durations at `--log-level` / `--access-logfile`; the fastest zero-code step is enabling gunicorn's access log format to include `%(t)s` etc. — but custom fields (cache hit, row counts already in `meta`) require the middleware. [^6]

**APM (Sentry / OTel / Datadog).** Sentry has a first-party Falcon integration (`sentry_sdk.init(..., traces_sample_rate=...)`, auto-enabled when `falcon` is installed) that creates a transaction per request and hooks the Falcon API classes. [^5] OpenTelemetry has `opentelemetry-instrumentation-falcon` (one `FalconInstrumentor().instrument()` call captures every request). [^6] Caveats: tracing overhead is real and version-sensitive — Sentry `enable_tracing=True` was reported to grow memory ~47 MB/hour in ASGI apps (pymalloc fragmentation) and frame-local serialization can block event loops for seconds in recent FastAPI issues; keep `traces_sample_rate` low (e.g. 0.1) and never enable Sentry *profiling* for every request. [^7] None of sentry/opentelemetry/structlog are currently installed in the repo venv. [^local]

**Hotspot identification for this repo (measured).** For `/api/history` with default filters (3 retailers, 45 newest files/retailer, all dates): `connect` 18 ms, `cur.execute` 2.43 s, `fetchall` 0.65 s, `pd.DataFrame` 0.38 s, `to_datetime` 0.08 s (425,115 rows). For `/api/history?all_history=true`: **14.96 s / 1,670,490 rows**. So ~65% is SQL execution, ~17% fetchall row-conversion, ~10% DataFrame construction — serialization (0.72 s records + 0.10 s orjson) and pandas groupbys (54–83 ms) are *not* the top of the profile for warm-enough payloads, but they dominate once the load is cached. [^local2] [^local5] For `/api/products/search` the current LIKE/ORDER BY body is fast (20 ms) after warm-up; a 687 ms cold call measured earlier is dominated by cold OS page-cache loads of `product_prices` index pages, not by the query — a boot-time warm-up (one query per hot path) fixes the first-request spikes. [^local6]

### 2. SQLite tuning for read-heavy multi-thread WSGI

**What the repo already does (verified):** WAL is persistent on `prices.db` (`journal_mode=wal`), launcher sets `synchronous=NORMAL`, `busy_timeout=5000`, `mmap_size` 256 MB env (but `sqlite_price_repository.get_db_connection` hardcodes 1 GB), `cache_size=-128000` (repo, 128 MB) vs launcher env `-64000` (64 MB), `temp_store=MEMORY`, `query_only=1`, URI `mode=ro`. The **DB file itself** has defaults (`cache_size=-2000`, `mmap_size=0`); tuning is per-connection, which is correct because SQLite's page cache is *per connection* private memory (shared-cache mode is discouraged by the SQLite author). [^local] [^13]

**WAL semantics worth keeping.** WAL gives concurrent readers + one writer; readers do not block writers and writers do not block readers. [^10] Two edge cases matter for this repo: (a) a *read-only* WAL database can only be opened when `-shm`/`-wal` files already exist or can be created, or when `immutable=1` is used — since `-shm`/`-wal` exist here (0.03 MB / 0 B on disk), `mode=ro` works today but will fail if the DB is copied to a read-only filesystem without those files; [^10] [^9] (b) Hynek Schlawack's TIL shows short-lived readers (open → one SELECT → close per process/thread) in WAL mode can hit rare `SQLITE_BUSY` during `-shm` lifecycle locking even with *zero* writes — his repro shows 7/6400 failures with WAL + busy_timeout=0 and 0 failures with busy_timeout=1 s (or DELETE mode). The repo's `busy_timeout=5000` already matches his fix; still, it is the *why* behind keeping connections long-lived (see below). [^11]

**Connection strategy: one per thread (thread-local), reused.** Python's `sqlite3` is compiled `threadsafety=3` in the repo's Python 3.14.7 (`sqlite3.threadsafety` → Serialized: connections may be shared across threads with full internal locking). [^8] Best practice for read-heavy servers remains **one connection per thread, stored in `threading.local()`**, created lazily and reused — this removes the measured ~20 ms connect+PRAGMA cost per request *and* the per-request `-shm` churn that triggers the WAL reader-lock edge case. [^15] The repo's `scripts/run_falcon_server.py` already defines `get_readonly_sqlite_connection(..., check_same_thread=False)` but **nothing in the app calls it**, and `sqlite_price_repository` opens/closes a fresh connection on every call (`get_db_connection` → `connect` → `close` in every function's `finally`). [^local] The repo's own benchmark script (`scripts/benchmark_db_queries.py`) already contains both a FIFO `ConnectionPool` and a thread-local strategy with check_same_thread toggle — the thread-local one matches the SQLite forum consensus that **a single connection must not be used by two threads simultaneously** (SQLite serializes a connection internally, negating concurrency) and that ThreadPoolExecutor/Falcon thread pools should each own a connection. [^16] [^15]

**cache_size / mmap_size.** `cache_size` is per-connection and in the correct ballpark already (64–128 MB). `mmap_size` maps up to N bytes of the DB into the process address space and reads go through the OS page cache (no user-kernel double copy); with several read-only connections sharing the same file, the OS page cache is the *real* shared cache, and each connection's private SQLite page cache sits on top. [^13] Since `prices.db` is 2.68 GB and the code maps at most 1 GB (`get_db_connection`) while the launcher env advertises 256 MB (`SQLITE_MMAP_SIZE` is ignored by the repository — a real inconsistency), the tail of the DB is never mmap'd; raising mmap to ≥2.8 GB (64-bit address space makes this free) removes the boundary, or document that only the hot index/table prefix needs mapping. [^local] [^13] Note `mmap_size` is a *maximum*; SQLite maps less when memory is contended and demotes to regular reads safely. [^9]

**Thread-scalability limits.** SQLite in WAL supports many concurrent readers and one writer; realistic deployment numbers cited in the wild are ~50k reads/s and ~10k writes/s on NVMe in WAL mode. [^33] The actual ceiling here is Python-side: (a) large `fetchall()`s convert every column to Python objects (measured ~140–175k rows/s end-to-end — the C engine is not the limit); (b) within one WSGI worker, CPU-bound pandas/orjson work contends for the GIL, so **processes (workers) scale CPU, threads scale I/O overlap** — for this app, `--workers 4 --threads 16` has 4× duplicated caches and per-worker cold-start; more workers amplifies the cache-miss storm on boot (see §4/§5). [^local2] [^16]

**Pragmas missing that are worth adding.** `PRAGMA cache_spill = OFF` is usually counterproductive for reads; the only cheap additions for this read-only workload: `PRAGMA mmap_size` larger (above), optionally `PRAGMA locking_mode = EXCLUSIVE` (not usable with `mode=ro` shared readers; skip), and keep `busy_timeout` at 5000. For **immutability** (never-written DB), `file:prices.db?mode=ro&immutable=1` skips all locking/shm work entirely — but only if the DB is guaranteed immutable at runtime; if scrapers rebuild `prices.db` in place, immutable would return stale pages. [^9] [^10]

### 3. Serialization (orjson vs alternatives; pandas → JSON-native)

**orjson is the right choice already installed.** Published benchmarks: orjson encodes ~8.7× faster than stdlib json on flat records (1,240 MB/s vs 142 MB/s on CPython 3.13) and ~3.2× faster decoding; [^17] in an 8-library benchmark (json, ujson, orjson, rapidjson, cysimdjson…) orjson won *every* load/dump across Python 3.8–3.13; [^18] a micro-benchmark on a small dict gave orjson ~2.8× ujson and ~5.4× stdlib. [^20] **msgspec** (typed structs, codegen C encoder) beats orjson by ~25% on flat records, ~64% on wide rows, and 2× on decode — but only when you define `msgspec.Struct` schemas instead of feeding dicts; the repo's dict-of-lists envelope would need per-payload struct definitions (date,retailer,product_id,product_name,category,price,source_file) to capture that win. [^17] [^21] ujson is "still fast but aging" (crash-prone, no numpy/datetime native support) — no reason to switch from orjson. [^17]

**When `resp.data` beats `resp.media` — already the case here.** In Falcon, `resp.media = obj` triggers the registered media handler (custom orjson handler in this repo) at response-time *per request*; `resp.data = bytes` injects pre-serialized bytes directly and is documented as the faster path when your content is already bytes ("If the content is already a byte string, use the `data` attribute instead (it's faster)"). [^22] [^23] [^25] The resources do both (`resp.media = envelope_dict; resp.data = raw_bytes`) — harmless (data wins) but wasteful: the full 77 MB dict is retained per cache entry alongside the bytes, doubling memory in `_response_cache` which has **no byte cap** (only 512 entries), while `_history_cache` (DataFrames) is byte-capped at 300 MB total / 120 MB per frame. [^local] Recommendation: drop `resp.media` on the byte-cache hit path (keep it only on the `except` fallback), or keep it but cap `_response_cache` by total bytes.

**Preparse/normalize pandas → JSON-native (already done well, one more idea).** The repo's `records_from_frame` uses vectorized per-column conversion (numpy `tolist()`, unique-date lookup for timestamps) and wraps output in `JsonSafeList` to skip the deep re-walk in `envelope()`. Measured on 310k rows: `records_from_frame` 0.72 s vs pandas `to_dict('records')` 1.71 s vs `to_json('records')` 0.54 s (but `to_json` gives a string and changes date formatting, and still requires orjson round-trip for the envelope — the byte contract stays with `records_from_frame` + `orjson.dumps` at 0.10 s). [^local5] The remaining ideas: (a) **column-major payloads** (`{"columns":[...], "data":[[...]]}`) — numpy columnar arrays serialize far faster than 310k dicts; it changes the API contract and the Svelte consumer, so only if the frontend can be updated ([^17] wide-row data shows orjson 780 MB/s but msgspec 1,280 MB/s on wide rows — dict-building is the tax); (b) memoize the `records_from_frame` output (JsonSafeList) per filter signature alongside the DataFrame — serialization then happens once per 300 s TTL instead of 0.7 s per request (the response byte cache already does this today, so the win is only for the *history* endpoint family that shares one DataFrame across 5 endpoints). [^local]

### 4. Caching

**In-process TTL cache (already in place, room to tune).** The repo hand-rolls stdlib-only TTL caches (`_history_cache` 300 s, `_parse_cache` 300 s, `_response_cache` 300 s / 512 entries) with RLock protection — intentionally stdlib-only (a "verifier boundary" comment). cachetools offers `TTLCache`/`LRUCache` with the same semantics but is **not installed**; there is little reason to swap for the existing bounded dicts unless the code wants `@cached` decorators. [^24] [^local] Real gaps: (a) **no byte cap on `_response_cache`** while entries can be ~77 MB+ (memory blow-up risk with 512 entries); (b) cache is per-worker, so 4 workers recompute the same 3.7 s load 4×; (c) TTL resets on hit (`move_to_end`) which is fine, but there is **no stampede protection** — after expiry, N concurrent threads all recompute the same 425k-row load (single-flight would help; the Redis guide shows the Lua single-flight pattern). [^26] [^local]

**Multi-worker shared cache: Redis (redis-py / valkey).** Redis cache-aside is the standard for read-heavy APIs: check Redis → miss → compute → `SET key value EX ttl`; sub-millisecond hot reads, bounded staleness, and shared across workers. [^26] Not installed in this repo; adding a Redis dependency contradicts the current stdlib-only verifier boundary, and the payloads are large (77 MB history) — Redis would need gzip'd bytes (2 MB) to be sane. Since the frontend is a browser dashboard, **HTTP caching (below) delivers the same cross-worker benefit with zero new infrastructure**; Redis is the follow-on if multiple API servers or cache purging on ingest are required. [^28]

**HTTP-level caching (missing entirely — biggest untapped win).** No `Cache-Control`, `ETag`, or `Last-Modified` headers are emitted by any endpoint (grep: 0 hits). [^local] RFC 9111 defines the semantics: `Cache-Control: public, max-age=300` lets browsers/CDNs serve repeated identical GETs with zero origin traffic; `ETag` + `If-None-Match` produce a 304 (0-byte body) when nothing changed; `s-maxage` splits browser vs CDN TTL; `stale-while-revalidate` hides recompute latency. [^29] [^30] [^28] For this API: every GET is keyed by query string and every response is already pre-serialized bytes in the cache, so an ETag can be derived for free (e.g., `SHA-256(raw_bytes)[:16]` or a version counter bumped on `clear_response_cache()`); a `TimingMiddleware`/`CacheMiddleware` can set `Cache-Control: public, max-age=300` when `cache_hit` is true and compute the ETag once per cached entry. Frontend Svelte SPA + a "single Streamlit rerun fires ~5 data requests with identical filters" (code comment) ⇒ repeated identical GETs are exactly the repo's usage pattern. [^local] Invalidation: TTL is 300 s today and `clear_inventory_cache()`/`clear_response_cache()` exist for tests; with HTTP caching, a new scrape can bump a global `data_version` (or `Cache-Tag`) so ETags change — the dual-write/invalidation literature says TTL + versioned ETag is the pragmatic pattern for infrequent ingest. [^31] [^34]

**Compression.** Nothing compresses today (grep: no gzip/brotli; neither `brotli` nor gzip middleware installed). Measured: 27.5 MB raw JSON → **0.7 MB gzip (2.4%) in 0.12 s**; a full 310k-row envelope (~77 MB) would gzip to ~2 MB. [^local3] Options in order of engineering cost: (1) terminate TLS/gzip at a reverse proxy (nginx) — the standard production answer; (2) a Falcon middleware that gzips `resp.data` when `Accept-Encoding: gzip` and length > ~1 KB, caching the gzipped bytes next to the raw bytes (gzip is deterministic — same cache key); (3) Granian/gunicorn have no built-in response compression, so a proxy or middleware is required for gunicorn/granian/waitress alike. [^37] [^35] Caveat: gzip of the biggest payloads costs ~0.3 s CPU per miss — cache the compressed variant; brotli compresses better but adds a dependency and CPU cost that usually belongs at the proxy/CDN. [^local3]

### 5. Compute reduction

**Precompute per data snapshot (the structural fix for cold loads).** The dashboard's expensive shapes (retailer averages, movers, coverage over time, category coverage, product search, plus the full filtered history) are pure functions of the ingested snapshot (`prices.db` / CSVs). The classic pattern is summary/materialized tables computed at ingest/write time: a 50 s GROUP BY over 500k rows became a 50 ms lookup when a summary table was maintained incrementally. [^32] For this repo: after `prices.db` is rebuilt, generate a **precomputed artifact set** — e.g., `InflationItems/precomputed/history_{defaults}.parquet|pickle`, `movers.parquet`, `retailer_averages.parquet`, `coverage.parquet` — and have workers load them at boot (or lazily once) instead of running the 2.4–15 s query per filter signature. Parquet needs `pyarrow` (not installed) or `fastparquet`; **pickle of the already-built DataFrames needs zero new deps and matches the pandas 3.x dtype handling already in the code**; alternatively extend the SQLite schema with aggregate tables so the load becomes a small indexed query. [^local] Keep the pandas code path as the computation engine for the artifact builder (`scripts/`), not inside the request path. The existing `load_movers_from_db`/`load_retailer_averages_from_db`/`load_coverage_from_db` functions must **not** be wired into resources as-is: measured 3.0–18.1 s for the same filters the pandas path does in ~2.5 s, because they scan all dates in range and do row-by-row `fetchall` into DataFrames. [^local4] [^36]

**Pagination / payload caps.** `/api/history` can return 425,115 rows (77 MB, meta warns "response may be large") or 1.67M rows with `all_history=true` (15 s load, ~300 MB JSON). [^local2] Even with perfect caching, the browser must download and the Svelte frontend must parse ~77 MB. Standard remedies: (a) make the default window genuinely bounded (the code already supports `start_date`/`end_date`/`max_files`; the default 60-day × 45-file window still returns 425k rows for the default 3 retailers — consider fewer files or page/cursor params); (b) add `limit`/`offset` or date-bucket pagination to `/api/history` (Zalando guidelines: SHOULD reduce bandwidth via pagination and compression; [^35] cursor/keyset pagination is the recommended pattern for date-orderable data [^36]); (c) **column pruning** — `HISTORY_COLUMNS` include `product_name` and `source_file` per row (~50% of row bytes are strings); a `fields` param or dropping `source_file` (already dropped in detail endpoints) cuts payload size proportionally; (d) feed the chart endpoints (movers, retailer-averages, coverage) from the small precomputed parquet/pickle frames — their total payloads are tiny (<1 MB) and their only cost today is the shared history load. [^local]

**Transfer + response-shape wins recap.** gzip (~40× smaller) [^local3] + HTTP caching (zero repeat origin hits) [^28] [^30] eliminate most real-world transfer cost before any query changes; precomputed artifacts eliminate the cold-load cost; pagination caps the worst case. The pandas groupby work itself (54–83 ms) is not worth optimizing further. [^local4]

## Recommended actions for the repo (prioritized)

**P0 — HTTP layer (days, zero risk, biggest measured win).**
1. Add a tiny `CacheMiddleware`/extend the existing ones in `inflation_dashboard/api/falcon_app.py`: set `Cache-Control: public, max-age=300` (align to `RESPONSE_CACHE_TTL_SECONDS`) and an `ETag` derived from the cached `raw_bytes` (store `etag = hashlib.sha256(raw_bytes).hexdigest()[:16]` next to the cache entry); honor `If-None-Match` → return `304 Not Modified` with empty body. Both values are already in memory when `get_cached_response()` hits. [^27] [^29] [^30]
2. Add gzip middleware (only for `Accept-Encoding: gzip` and `len(raw) > 1024`) that caches the gzipped bytes in `_response_cache` (deterministic) — measured 2.4% ratio makes history/coverage payloads ~40× smaller. [^37] [^35] If a reverse proxy (nginx/Caddy) fronts the API, do it there instead and only emit `Vary: Accept-Encoding`.

**P1 — Cold-load and connection plumbing (week).**
3. Per-thread reusable read-only connections: add a `threading.local()` holder in `sqlite_price_repository.get_db_connection` (lazy create, never close on request end, close only on worker shutdown), matching the strategy already prototyped in `scripts/benchmark_db_queries.py`; eliminates ~20 ms/request connect+PRAGMA and reduces WAL `-shm` churn. [^15] [^16] Unify the launcher env var (256 MB) with the repository's hardcoded pragmas (1 GB mmap, −128000 cache) — one config source. [^local]
4. Precompute per snapshot: new `scripts/precompute_artifacts.py` that runs once after `prices.db` build, writes pickle/parquet of (default + all_history) history frames, retailer averages, movers, coverage to `InflationItems/precomputed/`; resources load them at worker start (or lazy one-time) — removes the 2.4–15 s first-load per worker per filter signature without touching API response shapes. Do **not** route through `load_movers_from_db`/`load_retailer_averages_from_db`/`load_coverage_from_db` as-is (measured slower). [^local4] [^32]

**P2 — Observability (days, done before optimizing further).**
5. Add `TimingMiddleware` (perf_counter in `process_request` → `req.context`, log delta+route+cache_hit in `process_response`) — p50/p95 per endpoint per cache state in plain logs; no deps. [^4]
6. Install `py-spy` (`uv pip install py-spy` or pipx) and `snakeviz`; profile one cold `/api/history` and one `/api/products/search` request via `falcon.testing.TestClient` + cProfile for flame/deep views, and `py-spy top/record` on a worker under load (need `wrk`/`hey` installed). [^1] [^3] Keep `falcon-bench` (already in venv) for quick smoke throughput.
7. Optional APM only if actual ops require it: `sentry_sdk` Falcon integration at `traces_sample_rate=0.1` (profile only on demand) or `opentelemetry-instrumentation-falcon` + OTLP exporter; watch memory overhead (Sentry tracing memory growth reports). [^5] [^6] [^7]

**P3 — Response-shape and safety (when frontend team can coordinate).**
8. Cap `_response_cache` memory (currently unbounded bytes, 512 entries — a 77 MB × several entries risk); store only `raw_bytes` (+etag+gzip bytes) on the hit path, not the duplicated `envelope_dict`. [^local]
9. Pagination/`limit`/`fields` for `/api/history` (cursor on (retailer,date) or date-bucket + `limit`) and default-window trim so the worst case is bounded; drop `source_file` from the record rows (or make it opt-in) to cut ~half the string bytes. [^35] [^36]
10. Consider msgspec structs or column-major `{"columns","data"}` only if a future contract change is accepted — orjson stays the right serializer for the current dict-of-records format; do not add ujson. [^17] [^21]

## Gaps & uncertainty

- **SQL pushdown comparison is not apples-to-apples**: repo SQL aggregate functions aggregate *all* dates in range (≈490 output rows), while the pandas path aggregates only the 45 newest file-dates per retailer (135 output rows). The measured 3–18 s vs 2.5 s gap is still decisive against wiring them in, but a rewritten SQL path respecting "45 newest file dates" (e.g., joining the same CTE) could close some of the gap — untested. [single-source=local measurement]
- **Thread-scaling under Granian/gthread** (16 threads/worker) was not load-tested; GIL contention expectations for pandas+orjson are based on general Python behavior, not this repo's workload. [single-source=Tier3 forum claims]
- **mmap_size > file size behavior** (mapping 2.8 GB on a 2.68 GB DB) is safe per docs but the exact page-fault behavior on a 64-bit system is not measured here. [single-source=docs + oldmoe blog]
- **gzip middleware CPU at full 77 MB payloads** extrapolated from a 27.5 MB measurement (0.12 s ⇒ ~0.35 s for 77 MB); actual end-to-end including kernel copy unmeasured. Brotli quality/CPU numbers not measured (module absent).
- **ETag strategy** (content-hash vs version counter) unverified against the Svelte frontend's fetch behavior; 304 handling in browser cache is standard but the frontend may need no changes — unverified (no frontend test run).
- **Sentry/OTel overhead for this exact app** unmeasured (nothing installed); the memory-growth issue cited is for ASGI/apps and may not reproduce under WSGI Granian. Version-sensitive advice.
- **Granian vs gunicorn RPS gap (125k vs 9k)** is from Granian's own benchmark tables with a 10 KB static response; for this compute-bound pandas app, server overhead likely hides behind 2.4 s loads — the Anže blog confirms "no visible difference behind Nginx". Use as a capacity hint, not a substitute for load testing with the real endpoints. [single-source=Granian repo + one blog]
- **Precomputed artifact invalidation** (when scrapers rebuild `prices.db`) not specified: recommend rebuild artifacts in the same pipeline step as `prices.db` build, keyed by a snapshot hash; unverified in ops.
